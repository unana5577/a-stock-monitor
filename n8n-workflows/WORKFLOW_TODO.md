# n8n Workflow 优化记录与待办事项

本文档用于记录当前系统架构中涉及 n8n Workflow（特别是回补链路与标的管理）的局限性以及未来的改造计划。

## 1. 痛点：工作流范围“硬编码”与扩展性差
- **现状**：
  在 `M1-E-Backfill-Universal.json` 中，需要回补的核心标的清单（17 个标的）被硬编码在了 `Set` 节点（或类似的参数节点）中。
- **影响**：
  若未来系统需要新增监控标的（例如新增一个行业的 ETF），除了修改 Python 代码或配置文件外，还必须手动去 n8n 面板修改工作流节点。这种多处维护极易导致漏改和数据缺失。
- **改进方案**：
  将所有工作流中的标的列表读取改为**动态获取**。
  - 在项目中维护一份全局配置（例如 `config/symbols.json`）或者通过 `metadata` 接口暴露。
  - 工作流在执行前，先调用 API 或通过 Read File 节点获取该全量订阅清单，然后对清单中的每一个标的循环触发。

## 2. 痛点：冷启动回溯深度限制
- **现状**：
  底层脚本 `m1_backfill.py` 中写死了如果本地无数据（冷启动），默认仅向前回溯 60 天（`datetime.now() - timedelta(days=60)`）。
- **影响**：
  对于新加入的核心标的，只能看到最近两个月的日线，无法进行长周期的均线与生命周期计算。
- **改进方案**：
  修改 Python 脚本，支持通过命令行参数（如 `--start-date`）来覆盖默认的 60 天限制。如果是首次冷启动，可以通过 n8n 或手动传递特定的年份（如 `2020-01-01`）来一次性拉满历史日线。

## 3. 痛点：脚本“泛化匹配”的隐患
- **现状**：
  为了减少配置，`m1_backfill.py` 遇到不认识的 `symbol` 时，会通过前缀猜测（如 `sh5`、`sz1`）来判定它是否为 ETF，从而决定调用哪条数据抓取链路（腾讯大盘指数接口 vs 新浪 ETF 接口）。
- **影响**：
  对于没有规律前缀的指数（如新出的中小盘指数）无法兜底匹配，会导致直接报错。
- **改进方案**：
  取消基于前缀的隐式猜测。工作流或全局配置文件在下发标的清单时，必须显式携带 `type` 字段（如 `{"symbol": "sz399300", "type": "index"}`）。Python 脚本仅做纯粹的路由调度。
