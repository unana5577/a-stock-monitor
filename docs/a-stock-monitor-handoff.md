# a-stock-monitor 梳理与改造交接文档（对话整理）

> 用途：把当前问题、共识、改造方向与下一步执行清单沉淀下来，供 **code 模式**或后续执行者直接接手落地。
>
> 范围：仅 A 股（北京时间交易日口径），不考虑跨时区。

---

## 1. 现状与痛点（已确认“全对”）

### 1.1 数据与接口复杂
- 存在 **多个数据接口接入** + **备选接口**，且目前容易出现 **接口被混用/搞混**。
- 存在 **分时转日线**、**日线数据存储**、**warmup + 数据分析**、**清理缓存文件**等链路。
- **涨跌幅逻辑**存在口径要求。
- **大盘成交额**需要 **2 个接口拼接**（例如沪/深或两路来源拼接成总额），增加了对账与可追溯难度。

### 1.2 调度与可观测性不足
- 目前以 **cron 为主**，出现：
  - 定时任务没有按预期运行
  - 即使没跑通，也 **不知道卡在哪一步**
  - 失败/重试/告警不系统

### 1.3 工程结构偏乱
- 仓库中存在较多无用或历史文件，缺少系统化清理与目录规范。

---

## 2. 已达成的关键决策（后续执行必须遵守）

1) **调度方向**：引入 **n8n**，目标是 **完全替代 cron**（cron 仅保留兜底/逐步下线）。

2) **实现语言/形态**：接口与任务以 **Python 为主**。

3) **数据落盘**：已存在 `data/`，按 **日线缓存**与 **分时缓存**拆分（需要进一步规范与可追溯化）。

4) **涨跌幅口径**：优先采用 **交易所口径**（基于 `preClose` 计算，处理停牌/无成交需显式标识）。

---

## 3. 目标架构：先“止血”，再“结构化改造”

### 3.1 先止血（最小闭环：不再混接口 + 卡点可见）
建立三条硬约束：

1) **单入口 Runner（Pipeline Runner）**
- 所有任务必须从一个统一入口执行（CLI 或 HTTP 服务均可）。
- n8n 只负责 **编排/传参/重试/告警**，不直接调用散落脚本或内部函数。

2) **强制记录“接口标识 + 数据血缘”并落盘**
- 每次产物（分钟线/日线/中间结果）旁必须写 metadata（JSON）：
  - `providerId`：使用的接口/主备来源标识
  - `datasetId`：数据集标识（例如 minute、daily、turnover_total）
  - `day`：交易日（按北京时间交易日序列推导，不做 UTC/ISO 推导）
  - `asOf`：数据截至时间/回退标识
  - `runId`/`step`：本次运行链路标识

3) **每一步可观测（回答“卡在哪一步”）**
- 引入 `runId` 概念，每次运行产生可追溯状态（落盘 JSON 或 sqlite 均可）：
  - step 的 start/end/status/error/outputPaths
  - 失败可重试、可定位断点

> 术语：**数据血缘（Data Lineage）**
> - 含义：记录数据“从哪个源来、如何加工、何时生成、产物在哪”。
> - 作用：接口复杂时排障不靠猜；对账与追责可自动化。
> - 影响：后续扩接口越多，血缘越关键，否则不可控成本指数级上升。

### 3.2 再结构化改造（根治“接口搞混”）

1) **接口注册表（Interface Registry）**
- 把主/备接口、优先级、健康检查、字段映射统一配置与实现。
- 调用侧只能通过 `datasetId` 请求数据；由注册表决定实际 `providerId`。

2) **组合数据集（用于成交额拼接等）**
- 把“2 个接口拼接的大盘成交额”定义成显式的组合数据集 `turnover_total`：
  - 输入：`turnover_sh` + `turnover_sz`（示例）
  - 输出：`turnover_total`
  - metadata 中记录两路子源各自 `providerId/asOf`，便于定位差异来源

---

## 4. n8n 引入方式（推荐落地顺序）

### 4.1 n8n 负责
- 定时触发（Cron Trigger）
- 流程编排（Prepare → Fetch → Normalize → Transform → Warmup → QA → Cleanup）
- 失败重试与告警（邮件/消息等）

### 4.2 Python 负责（Runner 两种形态）
- **CLI Runner**（落地最快）：n8n Execute Command 调用统一命令入口
- **HTTP Runner（FastAPI 等）**（长期更稳）：n8n HTTP Request 调用 `POST /runStep`

建议：先 CLI 跑通关键路径，再升级 HTTP 化（减少环境差异与超时/并发问题）。

---

## 5. 涨跌幅（交易所口径）建议输出字段（防止后续口径互相污染）

建议数据中至少包含：
- `preClose`：昨收（明确来源/可追溯）
- `last/close`：最新价/收盘价
- `pct = (last - preClose) / preClose`
- `isHalt`：停牌或无成交标识（避免 pct 被误算）
- `pctBasis = "exchange"`：口径标识（未来若引入复权口径，可并存而不互相污染）

---

## 6. 自动对账（QA Workflow）：用机器替代人工逐条核对

新增每日 `qa` step，输出对账报告（JSON/CSV 均可）：
- 字段完整性：缺字段/单位异常
- 时间序列质量：分钟对齐、缺 bar 检测
- 口径一致性：用 `preClose` 复算 pct 与当前实现比对（误差阈值）
- 成交额一致性：`total ≈ sh + sz` 差异超阈值报警
- 主备对账（可选）：同一标的同一天主源 vs 备源差异分布

---

## 7. 工程清理（repo tidy）原则

目标：先产出“清理计划”，用户确认后再删除。
- 优先保留：入口代码、配置、数据落盘规则、对账逻辑、关键脚本
- 优先清理：构建产物、重复日志、历史导出、临时脚本、过期备份
- 强烈建议：先纳入 Git 版本控制（便于回滚）

交付物建议：
- `cleanup_plan.md`：可删/待确认/不可删三类清单
- `.gitignore`：避免缓存与产物再次污染仓库

---

## 8. 建议搭配的技能（skills）与用途

- `focus-keeper`：限定改造范围（调度/Runner/血缘落盘/可观测性），防止执行发散或误改口径。
- `bug-hunter`：系统性定位“cron 不跑/跑一半卡死/异常吞掉/落盘失败”等根因。
- `warn-tracker`：汇总运行输出中的告警/弃用/环境问题，形成可执行修复清单。
- `repo-tidy`：收敛目录结构、生成清理计划与 ignore 规则（删除需确认）。
- `git-sync`：为阶段性整理建立可回滚的里程碑提交。
