# M0 验收规格（唯一权威）

> **修订说明**：
> - 此文档为 M0 唯一验收标准。未通过所有 Checklist 前，严禁进入 M1/M2 或扩充新接口/分支。
> - 所有文件路径一律使用相对仓库根目录的相对路径。

适用范围：本仓库的 Runner（`python3 -m treasolo.runner run ...`）与 n8n 调用链路。M0 只验收两条路径（A/B），其余能力与分支一律后置，未在本文出现的内容不作为验收标准。

参考实现位置：
- Runner：`treasolo/runner.py`
- ETF 成交额 & 涨跌家数快照脚本：`scripts/market_snapshot_sina.py`
- 市场成交额（日线）回填脚本：`scripts/backfill_market_amount_daily.py`

## 1. 核心不变量（10 条以内）

1. **唯一交易日口径**：所有数据按北京时间（`Asia/Shanghai`）交易日推导。
2. **涨跌幅口径一致性**：`pct` 永远基于“昨收（`prevClose`） → 现价/收盘价”计算（严禁使用“今开→现价”）。
3. **成交额数据血缘**：全市场成交额（两市合并）与全市场 ETF 成交额分别获取，拼接为“ETF 成交额占比”时，必须处理分母为 0 或缺数边界。计算公式：`marketTotalAmount = sh000001.amount + sz399001.amount`，`etfSharePct = (etfTotalAmount / marketTotalAmount) * 100`（保留两位小数）。
4. **元数据（Metadata）绑定**：落盘文件必须附带 `.meta.json`，元数据与业务数据同生命周期。
5. **RunJournal 三态模型**：`run.status` 仅允许 `success`、`partial`、`failed`。
6. **Step 状态枚举**：`step.status` 仅允许 `success`、`failed`、`skipped`（前置依赖失败时出现 `skipped`）。
7. **Warning 阻断规则**：`warning.severity` 仅允许 `info`、`warn`、`error`。出现 `error` 时，所在 step 必须 `failed`，整个 run 必须 `failed`；出现 `warn` 但无 `error` 时，run 状态为 `partial`。
8. **保留策略**：日线数据追加（Append-Only），运行日志（RunJournal）等过程文件至少保留 30 天。

## 2. Runner 调用契约（n8n → Runner）

### 2.1 n8n 调用传参
n8n 需通过 CLI 或 HTTP 调用 Runner，并传递以下必要参数：
- `--day` 或 `day`: 指定业务日（格式 `YYYY-MM-DD`）。不传则默认为当前 `Asia/Shanghai` 时间。
- `--run-id` 或 `runId`: 追踪 ID（若不传，Runner 自动生成）。
- `--source` 或 `trigger`: 触发来源（例如 `n8n-cron`, `manual`）。

**路径选择（必须写死）**：Runner 必须能明确选择执行 M0 路径 A 或路径 B，避免“以为跑了 B 实际只跑了 A”：
- 约定 `source` 内必须携带 `pipelineId`，取值仅允许：`m0-A`、`m0-B`、`m0-AB`。
- 执行规则：`m0-A` 只执行第 5 节路径 A；`m0-B` 只执行第 5 节路径 B；`m0-AB`（默认）按顺序执行 A → B（A failed 时 B 为 `skipped`）。

### 2.2 Runner 标准 JSON 输出（stdout）
无论执行成功与否，Runner 必须向 stdout 输出如下格式的单行/多行合法 JSON（不得混杂非 JSON 文本）：

```json
{
  "runId": "20260416-123456-abc",
  "status": "success",
  "day": "2026-04-16",
  "asOf": "2026-04-16T15:00:00+08:00",
  "runJournalPath": "data/runs/2026-04-16/20260416-123456-abc.json",
  "warningsCount": 0,
  "errorsCount": 0,
  "outputs": [
    {
      "step": "market_amount",
      "path": "data/market/market-amount-daily.jsonl"
    }
  ]
}
```

## 3. 落盘规范与 Meta 结构

1. **业务数据产物**：保持 `.jsonl` 或 `.json` 原格式。
2. **Metadata 文件**：所有产物必须有对应的 `.meta.json` 旁路文件。
3. **Meta 必填字段**：
```json
{
  "runId": "20260416-123456-abc",
  "step": "market_amount",
  "datasetId": "market_amount_daily",
  "providerId": "akshare.fund_etf_hist_sina",
  "asOf": "2026-04-16T15:00:00+08:00",
  "fallbackReason": null
}
```

## 4. M0 验收 Checklist（必须回答以下 5 个问题）

对于任一报错，排查人员必须能通过 `runJournalPath` 或 `.meta.json` 回答：
1. **卡在哪一步（Step）？**：看 `step.name` 及 `step.status`（`failed`/`skipped`）。
2. **用了哪个接口（Provider）？**：看 `providerId`。
3. **数据的 `asOf` 是什么？**：看 meta 中的 `asOf`（确定是否拿了前天的数据）。
4. **产物在哪？**：看 `outputs.path`。
5. **失败原因是什么？**：看 `warnings` 中 `severity: "error"` 的 `message`，或 `fallbackReason`。

## 5. M0 验收路径（仅限 2 条）

### 路径 A：成交额两接口拼接 → 总额落盘 → 血缘可追溯
- **Step 1 (`market_amount_fetch`)**：调用接口获取 `sh000001` 与 `sz399001` 日线成交额，合并为 `marketTotalAmount`。
- **Step 2 (`etf_amount_fetch`)**：调用全市场 ETF 接口获取/更新数据，计算 `etfTotalAmount`。此步骤必须将 ETF 基础数据落盘。
- **Step 3 (`amount_merge`)**：计算 `etfSharePct = etfTotalAmount / marketTotalAmount * 100`。
- **产物（必须落盘）**：
  - `data/m0/<day>/<runId>/etf_amount_minute.jsonl` + `.meta.json`
  - `data/m0/<day>/<runId>/etf_amount_daily.jsonl` + `.meta.json`
  - `data/market/market-amount-daily.jsonl` + `.meta.json`（或同等级别合并产物文件，`datasetId: "market_amount_daily"`）。

**最小核对（可规模化，仅抽样 1 份当日数据）**
- 复算一致：`marketTotalAmount == sh000001.amount + sz399001.amount`（按不变量第 3 条公式复算）。
- 占比一致：`etfSharePct` 可由 `etfTotalAmount / marketTotalAmount * 100` 复算一致；若 `marketTotalAmount` 为 0 或缺数，必须按实现给出确定的边界行为（例如 `null` 或 `0`）并记录 warning（`severity=warn`）。
- 追溯齐全：ETF 分时与日线两个文件均存在，且对应 `.meta.json` 必含 `datasetId/providerId/asOf/runId/step/fallbackReason`。

### 路径 B：分钟线 → 日线 → 最小对账报告落盘
- **Step 1 (`minute_fetch`)**：获取某标的 `minute` 数据。
- **Step 2 (`minute_to_daily`)**：从分时序列的最后一条推导出 `daily.close`、`daily.high`、`daily.low`。
- **Step 3 (`daily_qa`)**：与历史 `prevClose` 对账，若涨跌幅口径校验失败，抛出 `severity: "error"` 阻断。
- **产物**：落盘至 `data/runs/<day>/<runId>-qa.json`（对账报告）。

**最小核对（可规模化，仅抽样 1 个 symbol）**
- 聚合自洽：`minute → daily` 的 `close/high/low/amount` 等字段与分钟序列自洽（`close=最后一分钟 close`，`high/low` 为分钟序列 max/min，`amount` 为分钟累计或求和，具体口径以实现为准但必须自洽）。
- 口径阻断：`daily_qa` 必须使用 `prevClose` 校验 `pct` 口径；校验不通过时必须产生 `severity=error` 且导致 `step.status=failed`、`run.status=failed`。
